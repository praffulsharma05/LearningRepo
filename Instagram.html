Why Build These 6 Tables First?

1. Master One-to-Many (1:N): USERS ➔ POSTS and POSTS ➔ COMMENTS show how a foreign key in the child table references the parent table.
2. Master Self-Referential Many-to-Many (M:N): FOLLOWS teaches you how one entity (Users) relates to itself through a bridge table with two foreign keys (follower_id and following_id).
3. Master Composite Unique Constraints: A user shouldn't be able to like the same post twice, nor follow the same account twice. UNIQUE(user_id, post_id) enforces this at the DB engine level.

1. Tracking Views: Row-Level Events vs Counter Column

Approach A: Adding columns (view_1, view_2...) ❌

Anti-pattern: Impossible to predict columns, alters table structure with every view, breaks 1st Normal Form (1NF), and causes catastrophic schema bloat.

Approach B: Separate Rows in post_views ✔️

Best for Analytics: Each view is an event record with user_id, post_id, and viewed_at. Allows queries like "Did user X watch post Y?" and "What hour has highest reach?"

Approach C: Denormalized posts.views_count ✔️

Best for Feed UI: Fetching a feed of 20 posts doing COUNT(*) FROM post_views for each post kills database IOPS. Storing an integer counter column gives O(1) instant display.

Hybrid Production Pattern: Use post_views rows for event intelligence + posts.views_count cached column updated via background workers.
2. Follower Table: followers vs follows

Why name it follows?

The table represents the action / relationship verb between two equal user entities. Both sides are users!

Self-Referential Foreign Keys:

• follower_id: The user who clicks "Follow" (e.g. Sweety)
• following_id: The account being followed (e.g. Prafful)
Both columns reference users.user_id.

Crucial Constraints:

1. UNIQUE(follower_id, following_id) prevents accidental double following.
2. CHECK (follower_id <> following_id) stops a user from following themselves.

Index Tip: Create index on follower_id (to get who I follow) AND index on following_id (to get who follows me).
3. Likes Architecture: Separate Tables vs Polymorphic Table

Option A: Polymorphic (Single likes Table)

Columns: like_id, user_id, target_id, target_type ('POST' or 'REEL').
Downside: Cannot use relational Foreign Key constraints in SQL without custom triggers or partial checks. Harder for relational integrity.

Option B: Distinct Tables (post_likes, reel_likes)

Provides strict Foreign Key referential integrity, clean indexes, separate disk partitioning, and zero table locking contention between Reels and Feed.

Verdict: Distinct tables (post_likes & reel_likes) are recommended for clean relational integrity and beginner-to-intermediate architecture.
4. Suggestions: Dynamic Algorithm vs Stored Table

Is suggestions a real-time relation?

No! Suggestions are ML / Graph Algorithm outputs calculated based on: mutual followers (friends of friends), phone contact sync, shared hashtags, and location proximity.

When to store in DB?

Precomputed recommendations are stored in a caching table with a decay timestamp: user_id, suggested_user_id, reason, score, created_at so the mobile app doesn't run expensive graph traversals on every app open.

Verdict: Treat suggestions as a materialized recommendation cache, refreshed periodically via background cron jobs.

PostgreSQL / MySQL Production DDL Script

Includes primary keys, foreign keys, cascade deletes, composite unique constraints, checks, and performance indexes.

-- ========================================================
-- INSTAGRAM DATABASE SCHEMA (Production-Ready DDL)
-- Compatible with PostgreSQL & MySQL 8.0+
-- ========================================================

-- 1. USERS TABLE
CREATE TABLE users (
    user_id BIGSERIAL PRIMARY KEY,
    username VARCHAR(30) UNIQUE NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    full_name VARCHAR(100),
    profile_picture VARCHAR(512),
    bio VARCHAR(150),
    website VARCHAR(255),
    is_verified BOOLEAN DEFAULT FALSE,
    is_private BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Index for username lookups and profile searches
CREATE INDEX idx_users_username ON users(username);

-- 2. POSTS TABLE
CREATE TABLE posts (
    post_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    caption TEXT,
    location VARCHAR(150),
    views_count BIGINT DEFAULT 0,
    likes_count BIGINT DEFAULT 0,
    comments_count BIGINT DEFAULT 0,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_posts_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_posts_created_at ON posts(created_at DESC);

-- 3. POST MEDIA (CAROUSELS SUPPORT)
CREATE TABLE post_media (
    media_id BIGSERIAL PRIMARY KEY,
    post_id BIGINT NOT NULL,
    media_url VARCHAR(512) NOT NULL,
    media_type VARCHAR(10) NOT NULL CHECK (media_type IN ('IMAGE', 'VIDEO')),
    carousel_order INT NOT NULL DEFAULT 1,
    CONSTRAINT fk_media_post FOREIGN KEY (post_id) REFERENCES posts(post_id) ON DELETE CASCADE
);

CREATE INDEX idx_post_media_post ON post_media(post_id, carousel_order);

-- 4. POST VIEWS (GRANULAR ANALYTICS EVENT LOG)
CREATE TABLE post_views (
    view_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL,
    viewed_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    duration_seconds INT DEFAULT 0,
    CONSTRAINT fk_post_views_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT fk_post_views_post FOREIGN KEY (post_id) REFERENCES posts(post_id) ON DELETE CASCADE
);

CREATE INDEX idx_post_views_post_id ON post_views(post_id);
CREATE INDEX idx_post_views_user_id ON post_views(user_id);

-- 5. REELS TABLE (SHORT-FORM VIDEO)
CREATE TABLE reels (
    reel_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    video_url VARCHAR(512) NOT NULL,
    caption TEXT,
    audio_title VARCHAR(150),
    duration_seconds INT NOT NULL,
    views_count BIGINT DEFAULT 0,
    likes_count BIGINT DEFAULT 0,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_reels_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

CREATE INDEX idx_reels_user_id ON reels(user_id);

-- 6. FOLLOWS TABLE (SOCIAL GRAPH)
CREATE TABLE follows (
    follow_id BIGSERIAL PRIMARY KEY,
    follower_id BIGINT NOT NULL,
    following_id BIGINT NOT NULL,
    status VARCHAR(15) DEFAULT 'ACCEPTED' CHECK (status IN ('ACCEPTED', 'PENDING')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_follows_follower FOREIGN KEY (follower_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT fk_follows_following FOREIGN KEY (following_id) REFERENCES users(user_id) ON DELETE CASCADE,
    -- Prevent following self
    CONSTRAINT chk_no_self_follow CHECK (follower_id <> following_id),
    -- Prevent duplicate follows
    CONSTRAINT uq_follower_following UNIQUE (follower_id, following_id)
);

CREATE INDEX idx_follows_follower ON follows(follower_id);
CREATE INDEX idx_follows_following ON follows(following_id);

-- 7. POST LIKES TABLE
CREATE TABLE post_likes (
    like_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_post_likes_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT fk_post_likes_post FOREIGN KEY (post_id) REFERENCES posts(post_id) ON DELETE CASCADE,
    -- Prevent liking the same post twice
    CONSTRAINT uq_post_user_like UNIQUE (user_id, post_id)
);

CREATE INDEX idx_post_likes_post ON post_likes(post_id);

-- 8. COMMENTS TABLE (THREADED / SELF-REFERENTIAL)
CREATE TABLE comments (
    comment_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL,
    parent_comment_id BIGINT,
    comment_text TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_comments_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT fk_comments_post FOREIGN KEY (post_id) REFERENCES posts(post_id) ON DELETE CASCADE,
    CONSTRAINT fk_comments_parent FOREIGN KEY (parent_comment_id) REFERENCES comments(comment_id) ON DELETE CASCADE
);

CREATE INDEX idx_comments_post ON comments(post_id);
CREATE INDEX idx_comments_parent ON comments(parent_comment_id);

-- 9. SAVES TABLE (BOOKMARKS)
CREATE TABLE saves (
    save_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_saves_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT fk_saves_post FOREIGN KEY (post_id) REFERENCES posts(post_id) ON DELETE CASCADE,
    CONSTRAINT uq_user_post_save UNIQUE (user_id, post_id)
);

CREATE INDEX idx_saves_user ON saves(user_id);

-- 10. STORIES TABLE (EPHEMERAL 24H TTL)
CREATE TABLE stories (
    story_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,

High-Scale API Design Standards

• Direct-to-S3 Uploads: Clients never upload high-resolution 10MB images or 50MB videos through the API servers. Instead, clients call POST /media/presigned-url and PUT binary blobs directly to Amazon S3 / Cloudflare R2.
• Cursor-Based Pagination: All feeds and comment lists use ?cursor=171928372&limit=20 rather than ?page=50 to avoid the costly OFFSET query degradation on billions of rows.
• Stateless JWT + Redis Session Blacklist: Microservices authenticate requests with short-lived (15 min) JWT access tokens and long-lived refresh tokens stored in Redis.

System Capacity Formulas (How to Calculate Server Numbers for 100k DAU)

1. Query Throughput (QPS Math)

• 100,000 users x 60 requests/day = 6,000,000 requests/day.
• Average QPS = 6,000,000 / 86,400s ≈ 70 req/sec.
• Peak QPS (evening traffic spike 5x) ≈ 350 – 500 QPS.
• Read-to-Write Ratio = 99:1 (Reads dominate).

2. Media Storage Sizing

• Assume 20% of users upload 1 photo/video daily = 20,000 uploads.
• Avg compressed media size = 1.2 MB.
• Daily Storage = 20,000 x 1.2 MB = 24 GB / day.
• Monthly Storage Growth = 24 GB x 30 = ~720 GB / month.

3. CDN Egress & Bandwidth

• Each user scrolls through 40 feed images/day.
• Total images viewed = 100k x 40 = 4,000,000 images/day.
• Optimized WebP image = ~250 KB.
• Daily Egress = 4M x 250 KB = 1,000 GB (1 TB / day).
