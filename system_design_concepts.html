What is a CDN?

A geographically distributed network of proxy servers that caches content (images, JS, CSS, video) close to end users, reducing latency from ~300ms to ~15ms.

  • Reduces Round-Trip Time (RTT)
  • Offloads 80-95% bandwidth from Origin
  • DDoS absorption at the edge

PoP & Edge Servers

PoP (Point of Presence) = physical data center at Internet Exchange Points. Edge Server = high-performance server inside PoP with SSD/RAM cache & TLS termination.

  • HTTP/2 & HTTP/3 (QUIC) enabled
  • TLS handshake terminated near user
  • WAF & Bot detection at edge

Anycast Routing

Hundreds of PoPs share the same IP address. BGP routing tables automatically deliver packets to the topologically closest healthy server — zero client config needed.

  • Auto-failover if PoP goes down
  • DDoS traffic distributed globally

Cache Invalidation

Hard Purge: Deletes immediately (origin spike risk).
Soft Purge: Serves stale while revalidating in background.
Cache-Tags: Atomic multi-page invalidation via surrogate keys.

  • Propagates globally in < 150ms
  • URL purge, Wildcard, Tag-based

2 CAP Theorem — Brewer's Theorem

Core Rule: In a distributed system, during a network Partition, you can only guarantee Consistency OR Availability — never both simultaneously. You must choose CP or AP.

    C["🔒 Consistency\nEvery read gets the\nmost recent write"]
    A["✅ Availability\nEvery request gets\na non-error response"]
    P["🔗 Partition Tolerance\nSystem works despite\nnetwork splits"]

    CAP --> C
    CAP --> A
    CAP --> P

    C ---|"CP Systems\nBlock writes until\nall replicas agree"| P
    A ---|"AP Systems\nServe stale data to\nstay responsive"| P
    C -.-|"CA (Theoretical)\nOnly possible with\nno network partition"| A

Real-World Database Examples

Database CAP Choice Consistency Model Best Use Case
MySQL / PostgreSQL (Single Primary) CA Strong consistency (ACID), not partition-tolerant by default Banking, Transactions
MongoDB (with majority write concern) CP Strong — blocks writes if majority of replicas unreachable Inventory, Order Management
HBase / Google Spanner CP Linearizable — uses TrueTime / Raft consensus Financial systems, Global banking
Cassandra AP Eventual consistency — always writable, reconciles later IoT sensors, Logging, Social feeds
DynamoDB (default) AP Eventually consistent reads; optional strongly consistent reads Cart, Session store, Leaderboards
CockroachDB CP Serializable — distributed SQL with Raft consensus Multi-region ACID transactions

C — Consistency

Every read returns the most recent write or an error. All nodes see the same data at the same time. Think of it as a single-copy illusion.

Example: After UPDATE balance=500, every node must return 500 immediately.

A — Availability

Every request receives a non-error response (might be stale data). The system never refuses to serve, even during failures.

Example: Cassandra always responds even if some nodes are partitioned — you may read stale data.

P — Partition Tolerance

System continues operating even when network messages between nodes are dropped. In real distributed systems, partitions WILL happen — P is non-negotiable.

Key insight: Since P is mandatory, you choose between CP or AP.

3 UUID — Why We Use It For Security

IDOR Attack (Insecure Direct Object Reference)

With auto-increment IDs, an attacker changes /api/user/42 to /api/user/43 and accesses another user's profile, orders, or medical records.

UUID fixes this: IDs become unguessable, so even without authorization checks, enumeration is impossible.

UUID in Database Design

Store as BINARY(16) in MySQL or native UUID type in PostgreSQL. Avoid VARCHAR(36) — wastes 2.25× storage and slows indexing.

Tip: Use UUIDv7 (time-ordered) for primary keys to preserve B-Tree insert performance. Use UUIDv4 for tokens/secrets.

Information Leakage Prevention

Sequential IDs leak: total record count (growth rate), creation order (timing attacks), and volume (competitor intelligence).

UUIDs reveal nothing about database size, order frequency, or user count.

Distributed ID Generation

Auto-increment requires a single coordinator (bottleneck). UUIDs can be generated independently on any node without coordination — critical in microservices & distributed databases.

Alternatives: Snowflake IDs (Twitter), ULID, KSUID, NanoID.

Load Balancing Strategies

Round Robin: Rotate requests equally.
Least Connections: Route to server with fewest active connections.
IP Hash: Same client always hits same server (session affinity).
Weighted: Powerful servers get more traffic.

Health Checks & Failover

Load balancers send periodic health probes (HTTP GET /health). If a server fails to respond, traffic is automatically rerouted to healthy nodes in < 10 seconds.

Key: Stateless servers enable instant failover — no session data lost.

Stateless vs Stateful

Stateless servers store zero user state locally. Sessions live in Redis/Memcached. Any server can handle any request — enables effortless horizontal scaling.

Stateful servers require sticky sessions, making scaling and failover difficult.

Auto-Scaling

Cloud platforms (AWS ASG, K8s HPA) monitor CPU/memory/request-rate and automatically add or remove server instances.

Scale-out at 70% CPU → spin up new containers.
Scale-in at 20% CPU → terminate idle instances to save cost.

1. High Availability

If the Primary crashes, a Replica is automatically promoted to new Primary within seconds. Zero downtime for users. This is called automatic failover.

RTO (Recovery Time): 10-30 seconds with orchestrators like Patroni, Orchestrator, or RDS Multi-AZ.

2. Read Scalability

Most apps are 80-90% reads, 10-20% writes. Replicas handle all read queries, spreading load. Adding a replica linearly increases read throughput.

Pattern: Write to Primary → Read from Replica (Read-After-Write consistency via session routing).

3. Geographic Distribution

Place replicas in regions close to users — US-East, EU-West, AP-South. Users read from the nearest replica with ~20ms latency instead of 200ms cross-ocean.

Writes still go to Primary region and asynchronously replicate outward.

4. Disaster Recovery

If an entire data center is destroyed (fire, flood), replicas in other regions hold a complete copy. RPO (Recovery Point Objective):

Sync replication: RPO = 0 (zero data loss).
Async replication: RPO = seconds of replication lag.

5. Analytics & Reporting

Run expensive analytics queries and reports against a dedicated read replica. This prevents heavy reporting workloads from slowing down the production Primary.

Pattern: ETL pipelines, BI dashboards, and batch jobs all point to the replica.

6. Replication Lag Caveat

Async replicas may be seconds behind the Primary. A user writes data and immediately reads from a replica — they might see stale data.

Fix: Read-your-own-writes consistency — route the writing user's reads to Primary for a few seconds after their write.
