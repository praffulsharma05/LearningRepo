LinkedIn Enterprise Database Architecture

LinkedIn Database Design & ER Model

A comprehensive professional relational schema organized across 4 primary domains: Identity & Profile, The Social Graph, Feed & Engagement, and Direct Messaging & Jobs.

Domain 1 • 1:1 & 1:N
Identity & Profile
users ➔ profiles (1:1 auth split), experiences, education, and normalized user_skills + endorsements.
Domain 2 • M:N Graph
The Social Graph
Symmetric 2-way connections (1st/2nd/3rd degree networks) with LEAST/GREATEST unique index + asymmetric follows.
Domain 3 • Content & Pulse
Feed & Engagement
posts, multi-reaction telemetry (LIKE, CELEBRATE, INSIGHTFUL), and self-referencing threaded comments.
Domain 4 • Enterprise & Chat
Messaging & Recruitment
Thread-centric conversations & messages + companies, job_postings, and job_applications pipeline.

How Cardinality Invariants Protect LinkedIn's Core Value
1. Auth vs. Public Identity Isolation (1:1): users.user_id ↔ profiles.user_id guarantees sensitive credentials (password hashes, multi-factor secrets, audit stamps) are never leaked during read-heavy profile lookups.
2. Reciprocal Social Graph (Symmetric M:N): connections enforces that professional relationship is bilateral (both agreed), protected by a compound unique constraint on (LEAST(requester_id, receiver_id), GREATEST(requester_id, receiver_id)) to avoid redundant duplicate rows.
3. Thread-Safe Messaging Architecture: By separating conversations from messages and bridging through conversation_participants, LinkedIn supports 1-on-1 InMail, recruiter outreach, and enterprise multi-party group chats seamlessly.
The 4 Architectural Pillars of LinkedIn
A high-level systems breakdown dissecting how each subsystem operates independently while maintaining strict relational integrity.

1. Identity & Profile Layer

Auth, Bio & Career History

Professional credibility requires structured, chronological history. Career roles (experiences) reference canonical company entities to power employer search and alumni networks. skills are deduplicated lookup nodes to avoid fragmenting "React" and "ReactJS", while skill_endorsements records which 1st-degree connection vouched for that competency.

users (1:1) profiles users (1:N) experiences users (1:N) education user_skills • endorsements

2. The Social Graph Layer

1st, 2nd & 3rd Degree Connections

Unlike Twitter/Instagram's purely asymmetric follow graph, LinkedIn's core value rests on mutual trust. connections records mutual agreements with states (PENDING → ACCEPTED). In parallel, follows handles one-way broadcast subscriptions to LinkedIn Top Voices, Creators, and Enterprise Company pages.

connections (Self-Ref M:N) LEAST/GREATEST Unique Key follows (Polymorphic Target) Graph BFS Indexing

3. Feed & Engagement Layer

Posts, Reactions & Threaded Trees

Content sharing supports text, image carousels, video, and PDF slide decks. Rather than a binary like, post_reactions tracks expressive business sentiments (LIKE, CELEBRATE, SUPPORT, INSIGHTFUL, FUNNY) with a strict UNIQUE(post_id, user_id) constraint. comments uses a self-referencing parent_id for nested replies.

posts (1:N) post_reactions Reaction Enum Telemetry comments.parent_id (Adjacency List) Degree-Based Feed Fanout

4. Messaging & Recruitment

Direct Messaging & Talent Pipeline

Recruiters post listings via job_postings tied to verified companies. Job seekers submit applications with S3 resume references. Direct communication is handled by a thread-based architecture: conversations → conversation_participants → messages, enabling real-time unread badges without locking entire mailboxes.

Workflow 1: Connection Request Lifecycle & Mutual Edge Formation
How connection invitations move from initial dispatch through receiver response, edge creation, and real-time graph index updates. 
sequenceDiagram
    autonumber
    actor UserA as Requester (User A)
    participant API as Connection API
    participant DB as Relational DB (connections)
    participant Graph as Social Graph Engine (Neo4j / In-Memory BFS)
    participant Push as Notification Service
    actor UserB as Receiver (User B)

    UserA->>API: POST /api/v1/connections/request { receiver_id: B, note: "Hi, let's connect!" }
    API->>DB: Check if connection exists (LEAST(A,B), GREATEST(A,B))
    alt Connection already exists
        DB-->>API: Conflict (409 Already connected / pending)
        API-->>UserA: "Request already pending or connected"
    else No duplicate found
        API->>DB: INSERT INTO connections (requester_id=A, receiver_id=B, status='PENDING')
        DB-->>API: 201 Created (conn_id)
        API->>Push: Enqueue Push Notification & Email Alert
        Push-->>UserB: "User A wants to connect with you!"
        API-->>UserA: Request Sent Successfully
    end

    Note over UserB,DB: User B logs in and reviews pending invitations
    UserB->>API: PATCH /api/v1/connections/:id/respond { action: 'ACCEPT' }
    API->>DB: UPDATE connections SET status='ACCEPTED', responded_at=NOW() WHERE conn_id=:id
    DB-->>API: 1 row affected
    API->>Graph: Invalidate 1st & 2nd degree caches for User A and User B
    API->>Push: Notify User A ("User B accepted your connection request")
    Push-->>UserA: Push Notification: You are now connected with User B

Critical Architectural Decisions & Engineering Tradeoffs
Deep-dive into why LinkedIn's schema is structured this way rather than naive monolithic or NoSQL approaches.
1. Splitting `users` & `profiles` into a 1:1 Relationship

Option A: Single Monolithic `users` Table

Stating credentials, emails, passwords alongside headlines, bios, locations, and profile avatars in one wide row.

Option B: Strict 1:1 Normalized Separation (Selected)

users contains only sensitive auth & security fields. profiles contains public presentation data with a unique user_id foreign key.

Verdict: Security Isolation & Cache Efficiency. Public profile reads never touch password hash memory, and profiles can be heavily cached in Redis without risking auth data leakage.
2. Mutual Connections vs. Asymmetric Follows

Option A: Single Generic `follows` Table

Treating every relationship as a directional follow, requiring two rows (A→B and B→A) to represent a mutual connection.

Option B: Dedicated `connections` + `follows` Models (Selected)

connections enforces reciprocal state (PENDING → ACCEPTED) with a composite unique key (LEAST(A,B), GREATEST(A,B)). follows handles one-way following for public figures and companies.

Verdict: Half the Storage & Zero Inconsistent States. Prevents orphaned one-way "half-connections" while maintaining distinct business rules for networking vs. content broadcasting.
3. Threaded Comments: Adjacency List vs. Materialized Path

Option A: Nested Sets or Closure Tables

Requires complex recursive triggers and heavy index rebalancing whenever a user inserts a reply in a popular viral thread.

Option B: Adjacency List with `parent_id` + Max Depth Cap (Selected)

comments.parent_id self-references the root comment. LinkedIn restricts UI nesting to 2 levels (Top Comment → Replies). Deeper replies are flattened visually.

Verdict: Maximum Write Throughput. Single WHERE post_id = ? AND parent_id IS NULL query loads root comments; replies are loaded asynchronously on demand without complex tree traversal.
4. Messaging: Thread-Centric vs. Flat Sender/Receiver

Option A: Flat Messages Table (sender_id, receiver_id)

Every query to compute an inbox must execute WHERE sender_id = X OR receiver_id = X GROUP BY GREATEST/LEAST, failing completely for 3+ person group chats.

Option B: 3-Tier Model: Conversations, Participants, Messages (Selected)

conversations holds thread metadata; conversation_participants tracks each member's last_read_at timestamp; messages references conv_id.

Verdict: High-Scale Unread Badges & Native Group Chats. Calculating unread count is a blazing fast COUNT(*) WHERE conv_id = ? AND sent_at > last_read_at.

Calculating Degrees of Separation: Why Naive SQL JOINs Crash at Scale
Consider user with 500 connections.
• 1st Degree: 500 profiles.
• 2nd Degree: $500 \times 500 = 250,000$ edges. A two-table self-join on connections produces a massive Cartesian footprint.
• 3rd Degree: $500 \times 500 \times 500 = 125,000,000$ potential paths.
Executing recursive SQL WITH RECURSIVE at query-time causes table scans and locks. Instead, production LinkedIn uses bidirectional Breadth-First Search (BFS) executed across compressed in-memory Roaring Bitmaps stored in cluster RAM!
Security Design & Threat-Mitigation Blueprint
The security controls that MUST be integrated around this schema and API surface: authentication, authorization, encryption, abuse prevention, secure media handling, and privacy/GDPR governance.
DEFENSE IN DEPTH • OWASP API TOP 10
1. Authentication & Session Security

Passwords hashed with Argon2id (or bcrypt cost ≥ 12) + per-user salt; never store or log plaintext. Short-lived JWT access tokens (5–15 min) + long-lived refresh tokens stored in rotated, revocable server-side families. Enforce TOTP/WebAuthn MFA for recruiters and admins.

Integrate: token rotation + reuse detection, device binding, and instant revocation on password change or logout-all.
2. Authorization & IDOR/BOLA Prevention

Every resource route (/profiles/:userId, /posts/:id, /conversations/:id/messages, /jobs/:id/applications) must verify the caller owns or is authorized for that object. Never trust an ID from the URL alone. Enforce row-level ownership checks and RBAC (job seeker / recruiter / company admin / moderator).

Integrate: policy middleware (e.g. Casbin/OPA) + Postgres Row-Level Security so chat members and recruiter-company links are re-checked on each request.
3. Encryption In Transit & At Rest

TLS 1.3 everywhere (HSTS, no downgrade). Disk/volume encryption at rest with KMS envelope keys. Sensitive columns (email, phone, MFA seeds, messages.body) encrypted at the application layer. Consider E2E encryption for private messaging since messages currently stores plaintext body.

Integrate: field-level crypto + key rotation; store only ciphertext and a tokenized email lookup hash for uniqueness checks.
4. Secure Media & Resume Handling

Never accept a raw client resume_url (SSRF + authorization bypass). Accept only a server-issued pre-signed object key, validate MIME/extension/size, and virus-scan uploads. Buckets are private; downloads use short-TTL pre-signed URLs and are audited.

Integrate: quarantine bucket → AV scan → promote; signed GET URLs expire in minutes and are bound to the requesting user.
5. Input Validation & Injection Defense

Parameterized queries / prepared statements only — no string-built SQL. Validate & whitelist enums at the boundary. Escape user content for XSS in feed rendering. Guard against SSRF (no fetching arbitrary user URLs like website or media_url server-side).

Integrate: strict schema validation (JSON Schema/Zod), output encoding, CSP headers, and an allow-list for external media domains.
6. Abuse Prevention & Rate Limiting

Apply per-user and per-IP rate limits on /auth/login, /auth/password/forgot, /connections/request, /posts/:id/reactions and message sends. Add account lockout / exponential backoff, CAPTCHA on anomalies, and WAF + bot detection at the edge.

Integrate: sliding-window limiter in Redis + idempotency keys to prevent duplicate applications and double-reactions.
7. Audit Logging & Monitoring

Append-only audit trail for auth events, permission changes, resume downloads, and admin actions. Centralized structured logs with correlation IDs, PII redaction, and real-time anomaly alerting.

Integrate: SIEM ingestion, immutable WORM log storage, and alerting on mass-scrape / credential-stuffing patterns.
8. Privacy Modes & Consent

Profile viewing modes (Public / Semi-Private / Private) and consent flags for personalized ads / data use. Honor data minimization and purpose limitation. A viewing_mode enum masks the actor on profile_views when private.

Integrate: consent ledger table, granular settings, and masked/anonymized analytics pipelines.
9. GDPR Right to Erasure (DSR Pipeline)

On deletion request, all PII (email, resume PDFs, summary, messages, experiences) must be purged within 30 days (GDPR Art. 17 / CCPA). Cascades handle relational rows; a worker scrubs object storage and search indices; a tombstone/deletion receipt is retained.

Integrate: DSR workflow + Kafka fan-out so PostgreSQL, S3, Elasticsearch and caches are all erased consistently.
10. Infra, Secrets & Supply Chain

Private subnets + security groups; least-privilege IAM roles per service; secrets in Vault/KMS (never in code or env files committed to git); dependency/container scanning and SBOM; regular key + certificate rotation.

Integrate: shift-left SAST/DAST in CI, signed images, and least-privilege DB users (app role cannot DROP/ALTER).

1 High comments.parent_id had a plain self-FK REFERENCES comments(comm_id). 4 Medium connections.status='BLOCKED' conflated blocking with a connection state. Blocking is directional and independent of a mutual connection; storing it in the same row loses who blocked whom and breaks unblock/authz logic. A single-column index on a low-cardinality flag has near-zero selectivity; the planner will ignore it. 1st-degree lookups need the user key. FIXED — replaced with (requester_id, status) and (receiver_id, status) composite indexes for both traversal directions.
6 Medium Canonical LEAST/GREATEST functional unique index while the header claimed "PostgreSQL / MySQL 8+". Functional indexes on raw expressions are PostgreSQL-only; MySQL needs generated columns. "Works on MySQL" was false and would fail at migration. FIXED — header re-scoped to PostgreSQL flagship + inline MySQL generated-column alternative added.
7 Medium Denormalized counters (reactions_count, comments_count, shares_count, endorsement_count) had no maintenance mechanism. Counters drift from reality without a trigger/job, producing wrong social proof and duplicate-reaction bugs. DOCUMENTED — maintain via DB triggers or an event consumer, in the same transaction as the write.
8 Medium posts.author_id only references users. Companies cannot author posts, yet enterprise pages post on LinkedIn — the model has no path for company-authored content without a schema change. DOCUMENTED — add a polymorphic author, or an author_type + optional company_id, with a check that exactly one author is set.
9 Low posts.content TEXT NOT NULL and messages.body TEXT NOT NULL. Media-only posts and attachment-only messages have no text; NOT NULL forces a dummy empty string and blocks legitimate cases. DOCUMENTED — relax to nullable + add a CHECK (content IS NOT NULL OR media_url IS NOT NULL) so at least one payload exists.
10 Low Table Dictionary drifted from the ERD/DDL (missing industry, headquarters, workplace_type, expires_at, shares_count, activities_societies, updated_at) and had wrong enums. Docs that disagree with the schema mislead every consumer and cause integration bugs (e.g. missing DEACTIVATED, REVIEWING, CONNECTIONS_ONLY). FIXED — aligned users.status, posts.visibility/media_type, job_applications.status, and added all missing columns to the dictionary.

11 Critical No authentication endpoints existed (no register/login/refresh/logout/reset). An "Identity" domain with no way to establish identity is unusable and left token lifecycle (rotation, revocation, MFA) undefined. FIXED — added Category 1 "Authentication & Session APIs" (6 endpoints) with Argon2id + rotating tokens.
12 High API accepted a raw client resume_url on POST /jobs/:id/apply. Classic SSRF + authorization bypass: attacker supplies an internal/foreign URL or references someone else's resume object. FIXED — endpoint now takes a server-issued resume_object_key from a pre-signed upload flow; validated + AV-scanned.
13 High API claimed 42 endpoints but only 23 were listed (10/8/12/12 labels vs 8/5/5/5 rows). Spec is the contract; inflated counts hide missing functionality (esp. no auth endpoints at all) and erode trust in the doc. FIXED — added Auth + missing CRUD/ATS endpoints and corrected counts so 6+9+7+9+11 = a real 42.
14 Medium Connection response used PATCH in the workflow but PUT (with an undefined .badge-method.patch class) in the API table; HTTP method was inconsistent. Method mismatch breaks client contracts and caching semantics; a partial status change is semantically PATCH, not PUT. FIXED — standardized on PATCH /connections/:id/respond, aligned the workflow, and added the missing .badge-method.patch CSS.
15 Medium CRUD gaps: no unfollow, no remove-connection, no GET/PUT/DELETE /posts/:id, no GET /posts/:id/comments, no recruiter ATS endpoints. Clients cannot complete basic lifecycle operations (unfollow, edit/delete a post, view an application funnel) — forcing undocumented back-channel calls. FIXED — added 12 missing endpoints across Graph, Feed, and Jobs categories.
16 Low WebSocket handshake documented a bearer token but no refresh/expiry or re-auth path; job search had no pagination contract. Long-lived sockets outlive short access tokens silently; search without a page contract leads to unbounded result sets. DOCUMENTED — sockets must reconnect-refresh on token expiry; all list endpoints require cursor pagination + server caps.
Verdict
The schema is fundamentally sound — the 1:1 auth/profile split, the symmetric connections graph, the threaded-comments adjacency list, and the 3-tier messaging model are all correct, production-grade choices. The real defects were three integrity holes (cross-post comment parents, non-participant message senders, client-supplied resume URLs), one broken index, a false MySQL portability claim, and documentation/spec drift (wrong enums, missing fields, and a 42-vs-23 endpoint gap with no auth API). All are corrected above and hardened by the new Security Design controls.
