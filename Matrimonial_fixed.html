The 3-Tier Multi-Manager Family Authorization Model
Separating authentication credentials from candidate matrimonial profiles allows family members (parents, siblings, candidates) to securely collaborate on the same matrimonial profile with strict permissions.
Fundamental Database Design Principle
Never conflate the Login Account (email, phone, credentials, KYC, sessions) with the Matrimonial Profile (biodata, age, caste, horoscopes, partner preferences). Many users can manage the same profile (father & daughter), and a single user can manage multiple profiles (father managing profiles for both son and daughter).
1. Users (Auth Accounts)
Authentication Boundary

Accounts used strictly for logging into the platform. Has credentials, active sessions, and KYC verification.

  • user_id (PK, UUID or BigInt)
  • Email and Phone uniqueness
  • Argon2id / Bcrypt password hash
  • Owns login_sessions & KYC verifications
2. Profiles (Matrimonial Data)
Biodata & Search Entity

Information about the individual seeking a partner. Discoverable in search and matchmaking algorithms.

  • profile_id (PK)
  • Display name, DOB, height, religion, education
  • Owns photos, addresses, preferences, hobbies
  • Target of interest proposals and matches
3. Profile Managers (M:N Bridge)
Authorization & RBAC

The join table resolving the M:N relationship with fine-grained permissions and family relationship tags.

  • Composite Unique on (profile_id, user_id)
  • relationship_to_profile: self, father, mother, etc.
  • permission_role: owner, editor, viewer
  • Status tracking: invited, active, revoked

-- 1. USERS: Authentication Accounts (Strictly separated from Profiles)
CREATE TABLE IF NOT EXISTS users (
    user_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) UNIQUE,
    phone VARCHAR(25) UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    role VARCHAR(30) DEFAULT 'member',
    account_status VARCHAR(30) DEFAULT 'pending_verification',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT chk_users_role CHECK (role IN ('member', 'admin', 'moderator')),
    CONSTRAINT chk_users_status CHECK (account_status IN ('pending', 'pending_verification', 'active', 'suspended', 'deleted')),
    CONSTRAINT chk_users_contact CHECK (email IS NOT NULL OR phone IS NOT NULL)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 2. PROFILES: Matrimonial Information (The person seeking marriage)
CREATE TABLE IF NOT EXISTS profiles (
    profile_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    display_name VARCHAR(150) NOT NULL,
    gender VARCHAR(20) NOT NULL,
    dob DATE NOT NULL,
    marital_status VARCHAR(50) NOT NULL,
    height_cm INT,
    religion VARCHAR(100),
    caste VARCHAR(100),
    sub_caste VARCHAR(100),
    mother_tongue VARCHAR(100),
    education VARCHAR(150),
    occupation VARCHAR(150),
    annual_income_range VARCHAR(50),
    family_type VARCHAR(50) DEFAULT 'nuclear',
    family_values VARCHAR(50) DEFAULT 'traditional',
    about_me TEXT,
    is_visible BOOLEAN DEFAULT TRUE,
    profile_status VARCHAR(30) DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT chk_profiles_gender CHECK (gender IN ('male', 'female', 'other')),
    CONSTRAINT chk_profiles_marital CHECK (marital_status IN ('never_married', 'divorced', 'widowed', 'separated')),
    CONSTRAINT chk_profiles_height CHECK (height_cm BETWEEN 100 AND 250),
    CONSTRAINT chk_profiles_family_type CHECK (family_type IN ('nuclear', 'joint')),
    CONSTRAINT chk_profiles_family_values CHECK (family_values IN ('traditional', 'moderate', 'liberal')),
    CONSTRAINT chk_profiles_status CHECK (profile_status IN ('active', 'hidden', 'deactivated'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 3. PROFILE_MANAGERS: Multi-Manager M:N Authorization Join Table
--    user_id is NULL while an invitation is pending (invitee may not have an account yet).
CREATE TABLE IF NOT EXISTS profile_managers (
    profile_manager_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    profile_id BIGINT UNSIGNED NOT NULL,
    user_id BIGINT UNSIGNED NULL,
    relationship_to_profile VARCHAR(50) NOT NULL,
    permission_role VARCHAR(30) NOT NULL DEFAULT 'editor',
    status VARCHAR(30) NOT NULL DEFAULT 'active',
    invited_email VARCHAR(255) NULL,
    invitation_token_hash VARCHAR(255) NULL,
    invitation_expires_at TIMESTAMP NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    -- 1 only for the single active owner of a profile, otherwise NULL (NULLs never collide in UNIQUE)
    active_owner TINYINT GENERATED ALWAYS AS (CASE WHEN permission_role = 'owner' AND status = 'active' THEN 1 END) STORED,
    CONSTRAINT uq_profile_user_manager UNIQUE (profile_id, user_id),
    CONSTRAINT uq_invitation_token UNIQUE (invitation_token_hash),
    CONSTRAINT uq_one_active_owner UNIQUE (profile_id, active_owner),
    CONSTRAINT fk_pm_profile FOREIGN KEY (profile_id) REFERENCES profiles(profile_id) ON DELETE CASCADE,
    CONSTRAINT fk_pm_user FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT chk_pm_relation CHECK (relationship_to_profile IN ('self', 'father', 'mother', 'brother', 'sister', 'relative', 'guardian')),
    CONSTRAINT chk_pm_role CHECK (permission_role IN ('owner', 'admin', 'editor', 'viewer')),
    CONSTRAINT chk_pm_status CHECK (status IN ('invited', 'active', 'revoked'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

Matrimonial Security Architecture & Data Protection
Critical safeguards protecting sensitive personal biodata, family privacy, and authentication vectors.

1. Modern Password Hashing

Passwords stored exclusively using Argon2id (or bcrypt with work factor ≥ 12). Raw passwords never touch database logs, and password hashes are never returned in JSON API responses.

2. Dynamic Photo & Contact Masking

Female/male candidate phone numbers and un-blurred photos are restricted behind authorized mutual match acceptances. Non-connected searchers only receive masked thumbnails and watermarked previews.

3. Server-Side RBAC Verification

Client-provided manager or admin roles are never trusted. Every profile mutation verifies whether the caller's user_id holds an active owner or editor role in profile_managers.

4. Anti-Enumeration & Rate Limiting

Login, password reset, and interest endpoints enforce strict rate limits (Redis token bucket: 5 attempts/min per IP/phone) to thwart brute-force password guessing and account harvesting.

5. Session Revocation on Security Events

Upon password change, role demotion, or account suspension, all active rows in login_sessions are revoked immediately, killing active refresh tokens across all remote devices.

6. Immutable Compliance Audit Logs

Security-critical events (manager invitations, role changes, profile bans, KYC verification decisions) are recorded with actor ID, IP address, and payload delta in audit_logs.
